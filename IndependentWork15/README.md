# Самостійна робота №15 — Делегати й лямбда-вирази: власні утиліти для колекцій

## Структура проєкту
- `Product.cs` — модель товару для демонстрації роботи з колекцією об'єктів.
- `CollectionUtils.cs` — статичний клас із узагальненими методами-утилітами `Map`, `MaxBy`, `Filter` та `ForEach`.
- `Program.cs` — демонстрація роботи всіх чотирьох методів на трьох різних типах колекцій (`List<int>`, `List<string>`, `List<Product>`) із використанням лямбда-виразів.

## Звіт

### 1. Чому делегати корисні для створення таких утиліт?
- **Відокремлення алгоритму обходу від бізнес-логіки:** сам метод-утиліта (`Map`, `Filter`, `MaxBy`, `ForEach`) відповідає лише за перебір колекції, перевірку на `null` та формування результату, тоді як конкретне правило обробки елемента передається ззовні через делегат (`Func`, `Predicate`, `Action`).
- **Повторне використання коду (принцип DRY):** замість написання десятків схожих циклів `foreach` для пошуку максимуму за ціною, вагою чи довжиною рядка, достатньо одного узагальненого методу `MaxBy`.
- **Гнучкість та розширюваність (принцип відкритості/закритості OCP):** поведінку методів можна змінювати під час виклику без редагування вихідного коду класу `CollectionUtils`.

### 2. Як лямбда-вирази спрощують виклик цих методів?
- **Компактність та читабельність:** замість оголошення окремих іменованих методів або громіздких анонімних делегатів (`delegate(Product p) { return p.Price > 1000; }`), логіка записується в один рядок безпосередньо в місці виклику (`p => p.Price > 1000`).
- **Автоматичне виведення типів (Type Inference):** компілятор C# самостійно визначає типи параметрів лямбда-виразу на основі типу елементів переданої колекції, тому не потрібно явно вказувати `TSource` чи `TKey`.
- **Замикання (Closures):** лямбда-вирази мають прямий доступ до локальних змінних методу, у якому вони створені, що дозволяє легко передавати динамічні параметри фільтрації чи перетворення без створення допоміжних класів.

### 3. Порівняння власних методів із вбудованими LINQ-операторами

| Власний метод | Аналог у LINQ | Виконання | Сигнатура та розширення | Особливості поведінки |
| :--- | :--- | :--- | :--- | :--- |
| `Map<TSource, TResult>` | `Enumerable.Select` | **Негайне (Eager)** — створює та заповнює новий `List<TResult>` одразу під час виклику. | Статичний метод класу `CollectionUtils` (викликається як `CollectionUtils.Map(...)`). | LINQ `Select` використовує **відкладене виконання (Deferred Execution)** через `yield return` і не виділяє пам'ять під проміжний список. |
| `MaxBy<T, TKey>` | `Enumerable.MaxBy` (з'явився у .NET 6) | **Негайне** — проходить усю колекцію за один прохід $O(n)$. | Приймає `Func<T, TKey>`, де `TKey : IComparable<TKey>`. | У LINQ `MaxBy` використовує `IComparer<TKey>` (дозволяє передати власний компаратор) і повертає `default` для порожніх колекцій посилальних типів замість винятку. |
| `Filter<T>` | `Enumerable.Where` | **Негайне** — повертає сформований `List<T>`. | Використовує делегат `Predicate<T>` (`bool(T)`). | LINQ `Where` використовує `Func<T, bool>`, працює як метод розширення (`extension method`), що дозволяє будувати ланцюжки викликів (`products.Where(...).Select(...)`). |
| `ForEach<T>` | `List<T>.ForEach` (у `IEnumerable<T>` стандартного LINQ немає) | **Негайне** — виконує побічну дію `Action<T>` для кожного елемента. | Працює з будь-яким `IEnumerable<T>`, а не лише з `List<T>`. | У стандартному LINQ свідомо відсутній `IEnumerable.ForEach`, оскільки філософія LINQ базується на чистих функціях без побічних ефектів. |

### Висновки
Реалізація класу `CollectionUtils` наочно демонструє, як працюють базові оператори LINQ «під капотом». Поєднання узагальнених типів (Generics), стандартних делегатів (`Func`, `Predicate`, `Action`) та лямбда-виразів дозволяє писати лаконічний, типобезпечний код без дублювання циклів. Водночас вбудовані оператори LINQ мають суттєві переваги у реальних проєктах завдяки методам розширення (ланцюжки запитів) та відкладеному виконанню (`yield return`), яке економить пам'ять під час обробки великих наборів даних.

## Відповіді на контрольні запитання

### 1. Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?
Делегати виступають типобезпечними посиланнями на методи, що дозволяє передавати алгоритм (логіку порівняння, фільтрації або перетворення) як звичайний параметр функції. У поєднанні з узагальненими типами (`<T>`) це дає змогу один раз написати структуру обробки колекції, а конкретну поведінку для будь-якого типу даних визначати динамічно під час виклику методу.

### 2. У чому різниця між `Func<T, TResult>`, `Action<T>` та `Predicate<T>`?
- **`Func<T, TResult>`** — делегат, який приймає один (або до 16) вхідних параметрів і **обов'язково повертає значення** типу `TResult` (останній параметр типу у списку завжди визначає тип результату). Використовується для перетворень (`Map`) та вибору ключів (`MaxBy`).
- **`Action<T>`** — делегат, який приймає вхідні параметри, але **нічого не повертає** (`void`). Використовується для виконання дій із побічним ефектом, наприклад виведення в консоль або зміни стану об'єкта (`ForEach`).
- **`Predicate<T>`** — спеціалізований делегат, який приймає один параметр типу `T` і **завжди повертає `bool`** (`true` або `false`). За функціональністю він еквівалентний `Func<T, bool>` і використовується для перевірки умов (`Filter`).

### 3. Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?
- **Повна типобезпека без приведення типів:** помилки невідповідності типів виявляються ще на етапі компіляції.
- **Висока продуктивність:** відсутній boxing/unboxing для значимих типів (`int`, `decimal`, `struct`).
- **Висока виразність і читабельність коду:** бізнес-логіка записується декларативно («що зробити з елементом»), а не імперативно («як організувати лічильник і цикл»).
- **Універсальність:** одна й та сама утиліта працює з будь-якими колекціями, що реалізують `IEnumerable<T>` (масивами, списками, множинами, чергами).

### 4. У яких випадках власні утиліти на кшталт `Map` чи `Filter` корисно реалізувати самостійно, навіть якщо існує LINQ?
- **Коли потрібне негайне виконання без зайвих алокацій:** у критичних до продуктивності ділянках коду (наприклад, у геймдеві або високочастотній обробці даних), де створення ітераторів стану (state machines) через `yield return` у LINQ створює небажане навантаження на збирач сміття (GC).
- **Для додавання специфічної бізнес-логіки або логування:** коли під час фільтрації чи мапінгу потрібно автоматично рахувати статистику, обробляти винятки або виконувати валідацію.
- **Для методів, яких немає у стандартному LINQ:** наприклад, `ForEach` для довільного `IEnumerable<T>`, пакетна обробка елементів або специфічні алгоритми агрегації.
