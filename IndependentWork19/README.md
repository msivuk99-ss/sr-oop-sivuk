# Самостійна робота №19 — Дизайн винятків і політики retry: теорія та кейси Polly

## Структура проєкту
- `OutOfStockException.cs` — власний клас винятку предметної області складу з трьома стандартними конструкторами та додатковими властивостями (`ProductSku`, `RequestedQuantity`, `AvailableQuantity`).
- `WarehouseService.cs` — сервіс резервування товарів, який генерує `OutOfStockException` при нестачі залишків.
- `PollyScenarios.cs` — реалізація трьох сценаріїв відмовостійкості за допомогою `ResiliencePipelineBuilder` бібліотеки Polly v8 (`Retry`, `Circuit Breaker`, `Timeout + Fallback`).
- `Program.cs` — демонстрація обробки власного винятку через `try-catch-finally` та запуск усіх сценаріїв Polly.

## Звіт про виконання

### 1. Власний тип винятку (`OutOfStockException`)
Для предметної області управління складом створено виняток `OutOfStockException`, успадкований від `System.Exception`. Клас містить усі три стандартні конструктори (`OutOfStockException()`, `OutOfStockException(string message)`, `OutOfStockException(string message, Exception innerException)`), а також конструктор із бізнес-контекстом, який заповнює властивості `ProductSku`, `RequestedQuantity` та `AvailableQuantity`. У блоці `try-catch-finally` спочатку перехоплюється специфічний `OutOfStockException` (із виведенням деталей нестачі товару), далі — загальний `Exception`, а блок `finally` гарантує фіксацію завершення операції.

### 2. Опис реалізованих сценаріїв Polly

#### Сценарій 1: `Retry` з експоненційною затримкою та Jitter (API служби доставки)
- **Опис проблеми відмовостійкості:** під час створення товарно-транспортної накладної через зовнішній HTTP API служби доставки можливі короткочасні мережеві збої або тимчасове перевантаження сервера (`503 Service Unavailable` / `HttpRequestException`). Одноразова відмова не означає, що сервіс непрацездатний — повторний запит через частку секунди зазвичай проходить успішно.
- **Обґрунтування обраної стратегії:** обрано стратегію `Retry` з експоненційним зростанням затримки (`DelayBackoffType.Exponential`) та випадковим відхиленням (`UseJitter = true`). Експоненційна затримка дає зовнішньому серверу час на відновлення, а `Jitter` запобігає одночасному «шторму» повторних запитів від багатьох клієнтів.
- **Фрагмент коду:**
```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(300),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args =>
        {
            Console.WriteLine($"[Retry] Спроба #{args.AttemptNumber + 1} невдала...");
            return default;
        }
    })
    .Build();
```
- **Опис виводу:** перша та друга спроби виклику API завершуються винятком `HttpRequestException`. Делегат `OnRetry` логує номер спроби та розраховану затримку перед повтором. На третій спробі виклик виконується успішно й повертає номер накладної `UA-2026-987654`.

#### Сценарій 2: `Circuit Breaker` (Захист від каскадних збоїв платіжного шлюзу)
- **Опис проблеми відмовостійкості:** якщо платіжний шлюз повністю вийшов з ладу на тривалий час, постійні повторні спроби (`Retry`) лише створюють зайве навантаження на мережу, блокують потоки нашого застосунку та заважають шлюзу відновитися.
- **Обґрунтування обраної стратегії:** обрано патерн `Circuit Breaker` (автоматичний вимикач). Після досягнення порогу помилок (`FailureRatio = 0.5`, `MinimumThroughput = 3`) він переводить ланцюг у стан **Open** на 2 секунди та миттєво відхиляє нові запити винятком `BrokenCircuitException` без реального звернення до платіжного шлюзу. Після паузи переходить у **Half-Open**, пропускає тестовий запит і при успіху повертається у робочий стан **Closed**.
- **Фрагмент коду:**
```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<InvalidOperationException>(),
        FailureRatio = 0.5,
        SamplingDuration = TimeSpan.FromSeconds(10),
        MinimumThroughput = 3,
        BreakDuration = TimeSpan.FromSeconds(2),
        OnOpened = args => { Console.WriteLine("[Circuit Breaker -> OPEN]"); return default; },
        OnHalfOpened = args => { Console.WriteLine("[Circuit Breaker -> HALF-OPEN]"); return default; },
        OnClosed = args => { Console.WriteLine("[Circuit Breaker -> CLOSED]"); return default; }
    })
    .Build();
```
- **Опис виводу:** перші 3 запити падають із `InvalidOperationException`, після чого спрацьовує подія `OnOpened`. Запити №4 та №5 відхиляються миттєво з `BrokenCircuitException` без виклику платіжного шлюзу. Після очікування 2.2 секунди під час запиту №6 спрацьовує `OnHalfOpened`, платіж проходить успішно, і ланцюг повертається у стан `Closed`.

#### Сценарій 3: Комбінація `Timeout + Fallback` (Отримання курсу валют)
- **Опис проблеми відмовостійкості:** зовнішній сервіс курсів валют може «зависнути» і відповідати занадто довго, що погіршить досвід користувача на сторінці оформлення замовлення. Водночас для відображення орієнтовної ціни критично важливо не показувати користувачеві екран помилки, а підставити останнє відоме кешоване значення.
- **Обґрунтування обраної стратегії:** поєднано зовнішню стратегію `Fallback` та внутрішню `Timeout` (350 мс). Якщо зовнішній API не встигає відповісти за 350 мс, `Timeout` скасовує операцію через `CancellationToken` і генерує `TimeoutRejectedException`, а `Fallback` перехоплює цей виняток і повертає безпечне резервне значення.
- **Фрагмент коду:**
```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>()
            .Handle<TimeoutRejectedException>()
            .Handle<HttpRequestException>(),
        FallbackAction = args =>
            Outcome.FromResultAsValueTask("1 USD = 41.50 UAH (резервне кешоване значення)")
    })
    .AddTimeout(new TimeoutStrategyOptions
    {
        Timeout = TimeSpan.FromMilliseconds(350)
    })
    .Build();
```
- **Опис виводу:** перший запит із затримкою 100 мс вкладається у ліміт 350 мс і повертає актуальний курс `41.85 UAH`. Другий запит із затримкою 1000 мс переривається на позначці 350 мс (`OnTimeout`), після чого `Fallback` повертає кешоване значення `41.50 UAH` без аварійного завершення програми.

### 3. Коли доцільно кидати виняток, а коли повертати `Result<T>`

Вибір між генерацією винятку та поверненням об'єкта результату (`Result<T>`) залежить від того, чи є помилка **винятковою технічною подією**, чи **очікуваним сценарієм бізнес-логіки**:
- **Винятки (`throw new ...Exception`)** доцільно використовувати тоді, коли метод не може виконати свій контракт через порушення інваріантів або інфраструктурні збої: розрив з'єднання з базою даних, недоступність мережі, відсутність критичного конфігураційного файлу, передача `null` туди, де це заборонено (`ArgumentNullException`). Винятки автоматично зупиняють подальше виконання невалідного потоку та зберігають повний стек викликів (*Stack Trace*) для діагностики.
- **Патерн `Result<T>`** (або повернення `bool` / `null` / спеціального статусу) варто застосовувати для **передбачуваних відмов**, які є частиною нормальної роботи системи: помилки валідації форми користувача, неправильний пароль, відсутність запису під час пошуку, нестача коштів або товару під час звичайної перевірки перед покупкою. Повернення `Result<T>` працює значно швидше (відсутня дорога процедура розкрутки стека викликів у CLR) і робить можливі помилки явними безпосередньо у сигнатурі методу.

### 4. Загальні висновки щодо переваг і обмежень Polly

**Переваги Polly:**
- **Декларативність та читабельність:** складні політики повторів, таймаутів і розмикання ланцюга описуються компактно через `ResiliencePipelineBuilder` без громіздких циклів `for` і `try-catch`.
- **Композиція стратегій:** можливість легко комбінувати стратегії в один конвеєр (наприклад, `Fallback` $\rightarrow$ `Retry` $\rightarrow$ `Circuit Breaker` $\rightarrow$ `Timeout`) із чітко визначеним порядком виконання.
- **Продумані механізми захисту:** вбудована підтримка експоненційних затримок із `Jitter`, потокобезпечного підрахунку статистики у `Circuit Breaker` та кооперативного скасування через `CancellationToken`.

**Обмеження та застереження:**
- **Додаткова складність налагодження:** при глибокій композиції кількох стратегій важче відстежити, на якому саме рівні конвеєра було перехоплено чи згенеровано виняток без детального логування (`OnRetry`, `OnTimeout`, `OnOpened`).
- **Ризик при неідемпотентних операціях:** неправильне налаштування `Retry` для операцій створення платежів чи списання коштів без ключів ідемпотентності може призвести до дублювання транзакцій.
- **Накладні витрати пам'яті та часу налаштування:** для найпростіших локальних перевірок використання зовнішньої бібліотеки є надлишковим порівняно зі звичайною умовою `if` або патерном `Result<T>`.

## Відповіді на контрольні запитання

### 1. Поясніть різницю між підходами «кидати виняток» та «повертати Result». Наведіть приклад для кожного.
- **«Кидати виняток» (`Exception`):** використовується для непередбачуваних, аномальних ситуацій, коли продовження нормального виконання неможливе, і потрібно перервати поточний потік керування та передати інформацію про збій вгору по стеку викликів.
  *Приклад:* при спробі зберегти замовлення в базу даних виникає `SqlException` через втрату зв'язку із сервером БД.
- **«Повертати `Result`»:** використовується для очікуваних бізнес-помилок, які є штатним результатом перевірки умов, без витрат на генерацію винятку та розкрутку стека.
  *Приклад:* метод реєстрації користувача `RegisterUser(email)` повертає `Result.Failure("Користувач із таким email уже існує")`, якщо адреса зайнята.

### 2. Які три стандартні конструктори рекомендується реалізовувати у власному типі винятку?
1. **Конструктор без параметрів:** `public CustomException()` — для створення винятку зі стандартним повідомленням.
2. **Конструктор із повідомленням:** `public CustomException(string message) : base(message)` — для передачі опису конкретної помилки.
3. **Конструктор із повідомленням та внутрішнім винятком:** `public CustomException(string message, Exception innerException) : base(message, innerException)` — для обгортання першопричини помилки (*Exception Wrapping*) без втрати початкового стека викликів.

### 3. Чим Circuit Breaker відрізняється від Retry? Коли який патерн доцільніший?
- **`Retry`** активно намагається виконати операцію знову через певні проміжки часу, припускаючи, що збій є **тимчасовим і швидко мине** (наприклад, короткочасна втрата пакета в мережі чи блокування рядка в БД).
- **`Circuit Breaker`** навпаки **припиняє спроби виклику** сервісу на певний час (`BreakDuration`), якщо кількість помилок перевищила поріг, припускаючи, що сервіс **«впав» надовго**.
- **Коли що обирати:** `Retry` доцільний при рідкісних одиничних збоях; `Circuit Breaker` необхідний для захисту системи від каскадних відмов і вичерпання потоків, коли зовнішній сервіс стабільно недоступний. На практиці їх часто комбінують.

### 4. Для чого потрібен Bulkhead і яку проблему він вирішує?
Патерн **Bulkhead (Перегородка)** ізолює ресурси (потоки, пули з'єднань, пам'ять) між різними частинами застосунку або зовнішніми сервісами, обмежуючи максимальну кількість одночасних викликів для конкретної операції. Він вирішує проблему **вичерпання ресурсів усього застосунку** через збій одного другорядного компонента: якщо повільний зовнішній API заблокує всі виділені для нього 10 потоків, решта 90 потоків сервера продовжать безперебійно обслуговувати інші запити користувачів.

### 5. Чому Jitter важливий при реалізації Retry з експоненційною затримкою?
Якщо тисячі клієнтів одночасно отримали помилку від сервера і використовують чисту експоненційну затримку (1 с, 2 с, 4 с), усі вони зроблять повторні запити в один і той самий момент часу, створюючи синхронні піки навантаження (**ефект «громового стада» / Thundering Herd**), які знову покладуть сервер. Додавання **Jitter** (випадкового часового зсуву) «розмазує» повторні запити в часі, дозволяючи серверу рівномірно обробити чергу та стабілізуватися.

### 6. Які ризики виникають при застосуванні Retry до неідемпотентної операції?
Неідемпотентна операція — це операція, повторне виконання якої змінює стан системи (наприклад, списання грошей із картки, створення нового замовлення, надсилання email). Якщо сервер встиг обробити запит, але відповідь загубилася в мережі через таймаут, автоматичний `Retry` відправить запит повторно. Це призведе до **подвійного списання коштів**, створення дублікатів замовлень або повторного надсилання сповіщень клієнту. Для безпечного використання `Retry` такі операції мають підтримувати **ключ ідемпотентності (Idempotency Key)**.
