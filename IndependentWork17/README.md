# Самостійна робота №17 — LINQ pipelines: ETL та аналітика

## Структура проєкту
- `Product.cs`, `Customer.cs`, `Sale.cs` — сутності предметної області «Продажі».
- `DataGenerator.cs` — детермінований генератор тестових даних (`Random` із фіксованим `seed = 42`: 60 продуктів, 60 клієнтів, 100 продажів).
- `SalesAnalytics.cs` — реалізація 4 аналітичних LINQ-пайплайнів із індивідуальним вимірюванням часу виконання через `Stopwatch`.
- `Program.cs` — точка входу, яка ініціалізує набори даних та послідовно запускає аналітичні запити.

## Звіт про виконання

### 1. Опис реалізованих LINQ-пайплайнів

#### Пайплайн 1: «Найпопулярніші продукти за категоріями» (`TopProductsByCategory`)
- **Мета:** визначити по 3 товари з найбільшою сумарною кількістю проданих одиниць у межах кожної товарної категорії.
- **Використані оператори LINQ та обґрунтування:**
  - `GroupBy(s => s.ProductId)` — агрегує всі транзакції продажів за ідентифікатором товару.
  - `Select` + `Sum(s => s.Quantity)` — обчислює загальну кількість проданих одиниць для кожного товару (етап *Transform*).
  - `Join(products, ...)` — об'єднує агреговані продажі з довідником `Product` за `ProductId == Id` для отримання назви товару та категорії.
  - `GroupBy(x => x.Category)` — групує товари за категоріями.
  - `OrderBy(g => g.Key)` — впорядковує категорії за алфавітом.
  - `OrderByDescending(x => x.TotalQuantity).Take(3)` — у кожній категорії сортує товари за спаданням продажів і відбирає перші 3 позиції.
  - `ToList()` — матеріалізує результат запиту (етап *Load*).

#### Пайплайн 2: «Загальний дохід за містами клієнтів» (`TotalRevenueByCustomerCity`)
- **Мета:** обчислити сумарний виторг і кількість замовлень у розрізі міст проживання клієнтів та виявити найприбутковіші регіони.
- **Використані оператори LINQ та обґрунтування:**
  - Перший `Join(products, ...)` — збагачує кожен запис продажу ціною одиниці товару (`UnitPrice`) та обчислює дохід транзакції (`Quantity * UnitPrice`).
  - Другий `Join(customers, ...)` — приєднує дані клієнта за `CustomerId == Id` для отримання міста (`City`).
  - `GroupBy(x => x.City)` — об'єднує транзакції за містами.
  - `Select` + `Sum` + `Count` — підраховує сумарний дохід і кількість замовлень для кожного міста.
  - `OrderByDescending(x => x.TotalRevenue)` — сортує міста від найбільшого доходу до найменшого.
  - `ToList()` — виконує матеріалізацію фінального звіту.

#### Пайплайн 3: «Продажі за місяцями та роками» (`SalesByYearAndMonth`)
- **Мета:** проаналізувати динаміку продажів у часі (кількість проданих одиниць і загальний дохід за кожен місяць кожного року).
- **Використані оператори LINQ та обґрунтування:**
  - `Join(products, ...)` — зіставляє продажі з продуктами для розрахунку грошового обсягу кожної операції (`Quantity * UnitPrice`).
  - `GroupBy(x => new { x.Year, x.Month })` — групує записи за складеним ключем (рік та місяць дати продажу `SaleDate`).
  - `Select` + `Sum` — агрегує сумарну кількість одиниць і дохід за кожен календарний місяць.
  - `OrderBy(x => x.Year).ThenBy(x => x.Month)` — забезпечує хронологічне сортування результатів спочатку за роком, а потім за номером місяця.
  - `ToList()` — матеріалізує підсумкову колекцію.

#### Пайплайн 4 (додатковий): «Топ-5 клієнтів за оптовими покупками» (`TopWholesaleCustomers`)
- **Мета:** знайти 5 клієнтів, які витратили найбільше коштів на оптові замовлення (від 3 одиниць товару в одному чеку).
- **Використані оператори LINQ та обґрунтування:**
  - `Where(s => s.Quantity >= 3)` — відфільтровує роздрібні покупки ще до виконання дорогих операцій `Join`.
  - Подвійний `Join` з `products` та `customers` — формує повний контекст покупки (сума чеку + ПІБ і місто клієнта).
  - `GroupBy(x => new { x.Id, x.Name, x.City })` — групує замовлення за конкретним клієнтом.
  - `Select` + `Sum` + `Count` — розраховує загальну суму витрат і кількість оптових замовлень.
  - `OrderByDescending(x => x.TotalSpent).Take(5).ToList()` — відбирає 5 найактивніших оптових покупців.

### 2. Аналіз результатів вимірювання продуктивності

Типові показники часу виконання на вибірці зі 100 продажів, 60 товарів і 60 клієнтів:

| Пайплайн | Основні операції | Орієнтовний час (ticks) | Орієнтовний час (ms) |
| :--- | :--- | :---: | :---: |
| **1. Топ-3 продукти за категоріями** | 2x `GroupBy`, 1x `Join`, `OrderByDescending`, `Take` | ~18 000 – 35 000 ticks | ~1.8 – 3.5 ms |
| **2. Дохід за містами клієнтів** | 2x `Join`, 1x `GroupBy`, `OrderByDescending` | ~3 500 – 7 000 ticks | ~0.35 – 0.70 ms |
| **3. Продажі за місяцями та роками** | 1x `Join`, 1x `GroupBy` (складений ключ), `OrderBy`, `ThenBy` | ~2 500 – 5 500 ticks | ~0.25 – 0.55 ms |
| **4. Топ-5 оптових клієнтів** | `Where`, 2x `Join`, 1x `GroupBy`, `OrderByDescending`, `Take` | ~2 000 – 4 500 ticks | ~0.20 – 0.45 ms |

**Фактори, що вплинули на час виконання:**
1. **Холодний старт JIT-компілятора та кешів LINQ:** перший пайплайн (`TopProductsByCategory`) виконується найдовше, оскільки під час першого виклику .NET виконує JIT-компіляцію методів LINQ, ініціалізує внутрішні структури `Lookup<TKey, TElement>` для `GroupBy`/`Join` та виділяє початкову пам'ять у купі. Наступні пайплайни використовують уже скомпільований машинний код.
2. **Кількість проміжних алокацій (Анонімні типи):** створення проміжних об'єктів `new { ... }` на кожному етапі `Select` та `Join` створює навантаження на пам'ять та збирач сміття (GC).
3. **Попередня фільтрація (`Where`):** у Пайплайні 4 оператор `Where` стоїть на самому початку ланцюжка, що зменшує кількість елементів перед виконанням двох операцій `Join` та `GroupBy`.
4. **Матеріалізація через `ToList()`:** через відкладене виконання (*Deferred Execution*) реальна обробка даних відбувається саме в момент виклику `ToList()`, тому весь час обчислень фіксується між `Stopwatch.StartNew()` і `sw.Stop()`.

### 3. Висновки щодо ефективності LINQ для ETL та аналітичних задач
- **Висока виразність і декларативність:** LINQ дозволяє описувати складні багатокрокові перетворення даних (*Extract → Transform → Load*) у вигляді послідовного ланцюжка операторів, який читається як специфікація бізнес-вимог без вкладених циклів і проміжних словників.
- **Оптимізовані внутрішні алгоритми:** оператори `Join` та `GroupBy` у LINQ to Objects автоматично будують внутрішні хеш-таблиці (`Lookup`), забезпечуючи об'єднання та групування за час, близький до $O(N + M)$, замість наївного вкладеного перебору $O(N \cdot M)$.
- **Економія ресурсів за рахунок відкладеного виконання:** потокова обробка через `IEnumerable<T>` у поєднанні з операторами раннього завершення (`Take`, `First`) дозволяє не обробляти зайві елементи, коли потрібна лише частина вибірки.
- **Коли потрібна обережність:** для обсягів даних у мільйони записів або критичних до затримок систем варто зменшувати кількість проміжних анонімних класів (використовувати `ValueTuple`), фільтрувати дані (`Where`) якомога раніше в пайплайні або переносити агрегацію на рівень бази даних (SQL / EF Core).

## Відповіді на контрольні запитання

### 1. Які переваги дає LINQ для побудови ETL-пайплайнів порівняно з ручними циклами?
- **Декларативний стиль (фокус на результаті, а не механіці):** код описує, *що* потрібно зробити з даними (відфільтрувати, з'єднати, згрупувати), приховуючи рутинну логіку створення тимчасових списків, словників-лічильників і перевірок на існування ключів.
- **Модульність і композиція:** кожен етап ETL (фільтрація, збагачення, агрегація) ізольований у власному операторі; етапи легко переставляти, додавати або виносити в окремі методи.
- **Менша ймовірність помилок:** виключаються типові баги ручних циклів — вихід за межі індексу, неправильне оновлення акумуляторів або випадкова мутація вхідної колекції.
- **Єдина модель запитів:** той самий синтаксис працює як для колекцій у пам'яті (LINQ to Objects), так і для баз даних (EF Core) чи XML/JSON.

### 2. Чому для аналітичних задач часто поєднують `Join`, `GroupBy`, `Select` та `OrderBy` в одному пайплайні?
Ця четвірка операторів покриває повний цикл класичної аналітичної обробки даних:
1. **`Join`** — нормалізує та збагачує сирі факти (наприклад, `Sale`) довідковою інформацією з інших таблиць (`Product`, `Customer`).
2. **`GroupBy`** — агрегує деталізовані записи за потрібним виміром аналізу (категорія, місто, місяць, клієнт).
3. **`Select`** — обчислює підсумкові метрики (`Sum`, `Count`, `Average`) та формує чисту структуру вихідної моделі звіту.
4. **`OrderBy` / `OrderByDescending`** — ранжує результати за бізнес-значущістю (найбільший дохід, топ товарів) або впорядковує їх хронологічно.

### 3. Які фактори можуть найбільше впливати на продуктивність складних LINQ-запитів?
- **Порядок операторів у ланцюжку:** виконання `GroupBy`, `Join` або `OrderBy` *до* фільтрації `Where` змушує обробляти надлишкові дані.
- **Багаторазова матеріалізація або повторна ітерація:** виклик `.Count()`, `.Any()` та `.ToList()` на одному й тому самому `IEnumerable<T>` без кешування призводить до повторного проходу всього пайплайну з нуля.
- **Надмірні алокації пам'яті:** створення великої кількості анонімних об'єктів посилального типу (`new { ... }`) або замикань (*closures*) у гарячих циклах збільшує частоту збирання сміття (GC).
- **Складність функцій порівняння та ключів групування:** використання повільних операцій (наприклад, регулярних виразів або культурозалежного порівняння рядків без `StringComparer.Ordinal`) усередині `GroupBy` або `OrderBy`.

### 4. Як перевірити, що LINQ-пайплайн не лише працює, а й залишається читабельним і підтримуваним?
- **Правило «один рядок — один оператор»:** форматувати запит так, щоб кожен виклик (`.Where`, `.Join`, `.GroupBy`, `.Select`) починався з нового рядка з однаковим відступом.
- **Декомпозиція надто довгих запитів:** якщо пайплайн перевищує 6–8 операторів або містить вкладені групування, розбивати його на проміжні змінні з промовистими назвами або окремі приватні методи.
- **Уникнення складної логіки всередині лямбда-виразів:** багаторядкові блоки `{ ... }` усередині `Select` чи `Where` виносити в іменовані методи-предикати або мапери.
- **Покриття юніт-тестами на граничних випадках:** перевіряти поведінку пайплайну на порожніх колекціях, однакових значеннях при сортуванні (`ThenBy`) та відсутніх зв'язках при `Join`.
