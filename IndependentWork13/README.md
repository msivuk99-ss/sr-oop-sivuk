# Самостійна робота №13 — Узагальнений кеш `Cache<TKey, TValue>` із тестами

## Структура рішення
- `IndependentWork7` — основний консольний проєкт із реалізацією узагальненого FIFO-кешу `Cache<TKey, TValue>`.
- `IndependentWork7.Tests` — проєкт юніт-тестів (xUnit) для перевірки методів `Add`, `Get`, `ContainsKey`, властивості `Count` та політики витіснення.

---

## Відповіді на контрольні запитання

### 1. Які переваги надає `Cache<TKey, TValue>` порівняно з окремими неузагальненими реалізаціями кешу?
- **Типобезпека на етапі компіляції:** компілятор гарантує, що в кеш потраплять лише ключі та значення визначених типів, що унеможливлює помилки приведення типів під час виконання (`InvalidCastException`).
- **Висока продуктивність (відсутність boxing/unboxing):** під час роботи зі значимими типами (`int`, `double`, структури) не відбувається пакування у тип `object` та виділення зайвої пам'яті в купі, що зменшує навантаження на збирач сміття (GC).
- **Повторне використання коду (принцип DRY):** замість створення окремих класів (`StringCache`, `IntUserCache` тощо) один узагальнений клас обслуговує будь-які комбінації типів.
- **Чистіший та зручніший код:** під час виклику `Get(key)` одразу повертається потрібний тип `TValue` без ручного приведення типів.

### 2. Чому для реалізації політики FIFO зручно поєднувати `Dictionary<TKey, TValue>` з `Queue<TKey>` або `LinkedList<TKey>`?
- **`Dictionary<TKey, TValue>`** забезпечує доступ, додавання та видалення елементів за ключем за середній час $O(1)$, проте не зберігає хронологічного порядку вставки елементів для їх витіснення.
- **`Queue<TKey>`** (або `LinkedList<TKey>`) зберігає послідовність додавання ключів за принципом *First In, First Out* і дозволяє за $O(1)$ отримати найстаріший ключ методом `Dequeue()`.
- **Поєднання обох колекцій** дозволяє зберегти складність $O(1)$ для всіх ключових операцій: пошуку, вставки та витіснення найстарішого елемента при переповненні.

### 3. У яких випадках метод `Get` повинен викидати `KeyNotFoundException`, а коли доцільніше використовувати підхід на кшталт `TryGetValue`?
- **Викидання `KeyNotFoundException` у `Get`** доцільне, коли відсутність ключа за бізнес-логікою є винятковою ситуацією або помилкою програми (наприклад, об'єкт обов'язково мав бути попередньо завантажений у кеш, і без нього подальша робота неможлива).
- **Підхід `TryGetValue`** краще застосовувати у стандартних сценаріях кешування (*cache-aside*), коли промах кешу (*cache miss*) є очікуваною штатною подією. Це дозволяє уникнути накладних витрат на генерацію та перехоплення винятків і одразу виконати резервне завантаження даних із бази даних або зовнішнього сервісу.

### 4. Які тести є критично важливими для перевірки політики витіснення елементів з кешу?
- **Перевищення ємності на один елемент:** заповнення кешу до `capacity` і додавання наступного елемента з перевіркою, що видалився саме найстаріший ключ, а новіші залишилися.
- **Послідовне витіснення кількох елементів поспіль:** перевірка коректності черги `FIFO` при багаторазовому переповненні.
- **Граничний випадок ємності `1`:** додавання другого елемента одразу має витісняти перший.
- **Оновлення значення для вже існуючого ключа при заповненому кеші:** має оновитися значення без видалення інших елементів та без зміни `Count`.
- **Поведінка після витіснення:** виклик `ContainsKey` для витісненого ключа має повертати `false`, а виклик `Get` — викидати `KeyNotFoundException`.
